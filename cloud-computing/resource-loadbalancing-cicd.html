Resource Pooling, Sharing & Provisioning

1. Resource Pooling ▼

Definisi: Resource pooling adalah pendekatan menggabungkan dan mengelola sumber daya komputasi seperti storage, processing power (CPU), memory, dan networking secara kolektif agar dapat dibagikan ke banyak pengguna atau aplikasi. Cloud provider mengalokasikan resource secara dinamis sesuai demand tanpa pengguna perlu mengetahui lokasi fisiknya.


Karakteristik Utama:

  • Abstraksi Lokasi - Pengguna tidak tahu dan tidak perlu tahu lokasi fisik resource yang mereka gunakan. Cloud menyembunyikan detail ini.
  • Alokasi Dinamis - Resource dialokasikan secara otomatis sesuai dengan kebutuhan workload pada saat itu.
  • Efisiensi - Mengurangi idle resource karena resource yang tidak digunakan oleh satu tenant dapat dialokasikan ke tenant lain.
  • Transparansi - Resource disajikan secara virtual kepada pengguna seolah-olah dedicated.

Proses Pooling: Physical servers di data center dipartisi melalui virtualization layer (seperti VMware ESXi, KVM, Xen, atau Hyper-V) menjadi virtual resources. Virtual resources ini kemudian dikelompokkan menjadi pool berdasarkan jenisnya: compute pool (CPU+RAM), storage pool (disk), dan network pool (bandwidth+switch virtual).

2. Arsitektur Resource Pool (3 Kategori) ▼

Resource pool architecture mengelompokkan resource ke dalam 3 kategori utama yang masing-masing memiliki karakteristik dan manajemen berbeda:


Pool TypeKomponenCara KerjaContoh
Compute/Server Pool CPU, RAM, Physical Machines Physical servers di-install OS dan hypervisor. VM dibuat di atasnya. Processor dan memory dari pool masing-masing di-attach ke VM sesuai kebutuhan. Resource dikembalikan ke pool saat VM tidak aktif. VM Pool di AWS EC2, Azure VMs, Google Compute Engine
Storage Pool HDD, SSD, SAN, NAS Disk fisik dipartisi dan diformat. Data yang ditulis ke virtual storage device sebenarnya disimpan di underlying physical disk. Storage pool dapat di-expand secara dinamis. AWS S3, Azure Blob Storage, Google Cloud Storage, Ceph

Hierarchical Organization: Untuk data center yang sangat besar, resource pool diorganisir secara hierarkis menggunakan parent-child relationship. Ini memastikan tidak ada single point of failure dan memudahkan manajemen.

3. Resource Sharing & Multi-Tenancy ▼

Resource Sharing memungkinkan cloud system mencapai tingkat utilisasi resource yang lebih tinggi. Ketika multiple applications berjalan di shared resource pool, rata-rata penggunaan setiap komponen meningkat karena aplikasi jarang mencapai peak demand secara bersamaan.


Multi-Tenancy adalah atribut sistem yang memungkinkan satu resource element mendukung multiple consumers (tenants) sambil menjaga isolasi antar tenant. Ini muncul dari prinsip ownership-free resource utilization - resource diakses dalam environment virtualized dan di-assign secara temporary dari shared pool.


Levels of Multi-Tenancy:

SaaS Application code base, database tables, functions Logical separation via consumer IDs/tenant IDs Salesforce, Gmail, Office 365, Slack

Tantangan Multi-Tenancy: Sharing resource mengurangi performance isolation, sehingga diperlukan resource management strategies yang efektif untuk menjaga Quality of Service (QoS). Tenant A yang menggunakan resource secara intensif tidak boleh mengganggu Tenant B.

4. Resource Provisioning (Static, Dynamic, Hybrid) ▼

Definisi: Resource provisioning adalah proses menyediakan dan mengalokasikan computing resources (CPU, memory, storage, network, applications) untuk memenuhi kebutuhan user atau aplikasi. Dalam cloud computing, ini merujuk pada alokasi resource dari cloud provider ke consumer.


ApproachDeskripsi DetailKapan DigunakanProsCons
Static Resource capacity ditetapkan fixed saat VM pertama kali diluncurkan dan tidak berubah selama VM beroperasi. Keputusan alokasi hanya dilakukan sekali di awal. Aplikasi dengan workload predictable dan consistent (e.g., internal company database) Simple, no runtime overhead, predictable cost Cannot handle demand spikes, inefficient (over-provisioning), limited scalability
Dynamic Resource capacity per VM dapat disesuaikan secara flexible dan on-demand selama runtime. Alokasi dan de-allocation terjadi precisely saat dibutuhkan. Provider mengelola centralized common resource pool. Cloud computing environments dengan workload yang berubah-ubah (e.g., e-commerce saat flash sale) Adaptif, pay-per-usage billing, scalable, zero-downtime migration via live VM migration Runtime overhead dari ongoing allocation decisions, minor system delays
Hybrid Kombinasi: static provisioning di awal (initial VM creation) kemudian beralih ke dynamic provisioning untuk menangani perubahan workload. Real-time scenarios dengan baseline workload yang stabil tapi occasional spikes Balance efficiency and flexibility, reduced overhead compared to pure dynamic Lebih kompleks, memerlukan monitoring dan threshold configuration

Autonomic Resource Provisioning: Dalam cloud modern, provisioning dilakukan secara otomatis menggunakan AI/ML techniques. Sistem memonitor workload patterns dan secara otomatis menambah/mengurangi resource tanpa manual intervention.


Zero-Downtime Architecture: Dynamic provisioning memungkinkan runtime replacement of computing resources. Jika physical server hosting multiple VMs crash, sistem secara otomatis memindahkan VM yang berjalan ke physical server baru melalui Live VM Migration tanpa downtime.

5. Provisioning Plans & SLA ▼

Short-Term On-Demand Plan:

  • Resource dialokasikan flexible on short-term basis
  • Saat demand naik, resource ditambah; saat turun, resource dikembalikan ke free pool
  • Billing: pay-per-usage (dibayar sesuai yang digunakan)
  • Menggunakan dynamic provisioning approach
  • Cocok untuk: workload unpredictable, development/testing environments, seasonal applications
  • Risiko: performance bergantung pada provider capability untuk memprediksi collective resource demand selama peak

Long-Term Reservation Plan (Advance Provisioning):

  • Consumer dan provider membuat service contract yang menspesifikasikan resource needs
  • Provider secara proaktif menyediakan dan menyisihkan resource dari pool untuk memenuhi kebutuhan consumer, terutama saat peak demand
  • Billing: fixed one-time fee untuk durasi tertentu (bulan/tahun)
  • Dari perspektif provider: reduced computational complexity dan lower costs karena maximum resource commitment diketahui di awal
  • Cocok untuk: workload predictable, production systems dengan SLA ketat
  • Risiko: jika consumer underestimate resource needs, aplikasi kehabisan resource; jika overestimate, ada waste

Service Level Agreement (SLA):

SLA adalah kontrak formal antara cloud consumer dan provider yang mendefinisikan:

  • Expected capacity: Berapa CPU, RAM, storage, bandwidth yang dijamin
  • Availability: Uptime guarantee (e.g., 99.9%, 99.99%, 99.999%)
  • Performance metrics: Response time, throughput, latency
  • Penalties: Kompensasi jika provider gagal memenuhi SLA (e.g., service credits)
  • Security: Data protection, encryption, compliance requirements

Provider menggunakan SLA untuk estimate resource needs dan melakukan resource mapping - yaitu menempatkan VM dari consumer ke physical infrastructure yang tersedia.

Resource Scaling & Load Balancing

1. Konsep Resource Scaling ▼

Definisi: Resource scaling adalah kemampuan cloud system untuk menyesuaikan (menambah atau mengurangi) computing resources secara otomatis atau manual berdasarkan workload demand. Scaling dapat melibatkan penambahan/pengurangan CPU, RAM, storage, atau server instances.


Kenapa Scaling Penting?

  • High traffic memerlukan lebih banyak resource untuk menjaga performance
  • Low traffic memerlukan lebih sedikit resource untuk menghemat cost
  • Scaling memastikan: good performance, cost efficiency, dan no downtime

Scalability vs Elasticity:

  • Scalability - Kemampuan sistem untuk handle growing amount of work (scale up/out)
  • Elasticity - Kemampuan untuk secara otomatis scale up dan scale down sesuai demand real-time
2. Vertical Scaling (Scale Up/Down) ▼

Definisi: Vertical scaling adalah menambah atau mengurangi kapasitas dari existing server/instance tanpa menambah jumlah server. Ini berarti meningkatkan/menurunkan RAM, CPU cores, storage capacity, atau network bandwidth pada satu mesin.

4. Hybrid Scaling ▼

Definisi: Hybrid scaling adalah kombinasi dari vertical scaling dan horizontal scaling. Sistem pertama kali di-scale vertically sampai batas hardware, kemudian di-scale horizontally dengan menambah lebih banyak instances.


Alur Hybrid Scaling:

  1. Mulai dengan 1 server kecil (vertical: small)
  2. Naikkan kapasitas server tersebut (vertical: medium -> large)
  3. Saat mencapai batas vertical, tambah server ke-2, ke-3 (horizontal)
  4. Setiap server baru juga bisa di-scale vertically jika perlu

Kapan Digunakan: Applications dengan baseline workload yang cukup besar (perlu vertical) tapi juga mengalami traffic spikes (perlu horizontal). Contoh: E-commerce platform, video streaming services.

5. Elastic Computing ▼

Definisi: Elastic computing adalah kemampuan customer untuk secara dinamis mengubah alokasi server - menambah server saat peak times dan mengurangi saat tidak dibutuhkan. Ini adalah dynamic service yang fully software-managed.


Karakteristik Elastic Computing:

  • Rapid creation and removal: VMs dapat dibuat atau dihapus tanpa perlu mengubah atau reboot physical servers
  • Physical sharing: Multiple virtualized servers dapat beroperasi concurrently pada satu physical server
  • Logical isolation: Meski berjalan pada satu physical server, setiap virtualized server completely isolated dari yang lain
  • Virtualized servers: Menawarkan fast, flexible allocation at low cost

Auto-Scaling: Dalam praktik modern, elastic computing diimplementasikan melalui auto-scaling groups/policies yang memonitor metrics (CPU utilization, request count, queue depth) dan secara otomatis menambah/mengurangi instances berdasarkan thresholds yang ditentukan.

6. Load Balancing - Konsep Dasar ▼

Definisi: Load balancing adalah distribusi workload secara merata di across multiple servers untuk ensure optimal resource utilization, minimize response time, dan prevent server overload.


Mengapa Load Balancer Diperlukan?

  • Website harus didesain untuk memproses banyak independent requests simultaneously
  • Bagaimana website scale untuk accommodate thousands of users? -> Load Balancer
  • Load balancer mendistribusikan incoming network traffic ke multiple backend servers

Karakteristik Load Balancing:

  • Jika site memiliki N servers, setiap server menangani approximately 1/N of the customers
  • Load balancer ensures all communication dari given customer goes to the same server (session persistence/stickiness)
  • Site dapat di-expand dengan menambah additional servers; load balancer secara otomatis includes new servers

7. Hierarchical Load Balancing ▼

Untuk large-scale data center, single load balancer tidak cukup. Diperlukan struktur hierarchical dari primary ke secondary load balancers.


Struktur Hierarki:

  • Primary Load Balancer (Top): Menangani 100% incoming traffic. Ini adalah single entry point dari internet.
  • Secondary Load Balancers (Middle): Setiap secondary LB menangani 1/P dari traffic, di mana P = jumlah pods (groups of racks).
  • Servers (Bottom): Dalam setiap pod yang berisi R racks, setiap link dari rack ke pod LB menangani 1/(P*R) dari total traffic.

Trade-off: Links near the top of hierarchy carry more traffic than links farther away. Primary LB adalah bottleneck potensial. Solusi: menggunakan multiple primary LBs dengan DNS round-robin atau anycast.

High Availability (HA)

1. Definisi High Availability ▼

Definisi: High Availability (HA) adalah kemampuan sistem untuk tetap operational dan accessible meskipun terjadi failures pada komponen hardware, software, atau network. Tujuannya adalah memastikan minimal downtime dan continuous service delivery.


Mengapa HA Penting?

  • Hardware failures tidak dapat dihindari (disk crash, memory failure, network outage)
  • Software bugs dapat menyebabkan service crashes
  • Human errors dalam operations dapat menyebabkan downtime
  • Downtime = lost revenue + damaged reputation + violated SLA

Layer 2: Services - 5 komponen kunci:

  • Monitoring: Continuous health checks, performance metrics collection, alerting systems (Prometheus, Grafana, Nagios)
  • Redundancy: Duplicate critical components sehingga jika satu gagal, yang lain mengambil alih (active-passive atau active-active)
  • Replication: Membuat copies data/application state di multiple nodes secara real-time atau near-real-time
  • Failure Detection: Mechanisms untuk mendeteksi failures secepat mungkin (heartbeat, ping, watchdog timers, health check endpoints)
  • Recovery: Proses failover ke backup systems, automatic restart, data restoration dari backups

Layer 3: Underlying Technologies - Foundation HA:

  • Multi-core Processors: Memungkinkan parallel processing dan fault isolation. Jika satu core fail, yang lain masih operational.
  • Virtualization: VM isolation memastikan failure di satu VM tidak mempengaruhi VM lain. Live migration memungkinkan moving VMs dari failing host ke healthy host tanpa downtime.
  • Storage System: RAID untuk disk redundancy, SAN/NAS untuk network storage, distributed storage systems (Ceph, GlusterFS) untuk data replication across nodes.
3. Redundancy Strategies ▼

Active-Passive Redundancy:

  • Satu node active melayani traffic, satu atau lebih node passive standby
  • Passive nodes tidak melayani traffic tapi selalu synchronized dengan active node
  • Ketika active node fail, passive node di-promote menjadi active (failover)
  • Contoh: MySQL Master-Slave replication, Windows Server Failover Cluster
  • Trade-off: Resource idle (passive nodes tidak digunakan), tapi failover cepat karena data sudah synchronized

Active-Active Redundancy:

  • Semua nodes active dan melayani traffic simultaneously
  • Load balancer mendistribusikan traffic ke semua nodes
  • Jika satu node fail, traffic di-redirect ke nodes yang masih active
  • Contoh: Web server clusters, database sharding, microservices
  • Trade-off: Tidak ada resource idle, tapi memerlukan careful data synchronization dan conflict resolution

N+1 Redundancy:

  • N nodes active + 1 spare node untuk failover
  • Lebih cost-efficient daripada 1:1 active-passive
  • Spare node bisa melayani traffic ringan atau digunakan untuk maintenance

5. Recovery Techniques ▼

Failover: Proses switching dari failed primary system ke standby/secondary system. Dapat dilakukan secara:

  • Automatic Failover: System mendeteksi failure dan melakukan switch tanpa human intervention (e.g., keepalived, Pacemaker, Kubernetes self-healing)
  • Manual Failover: Administrator secara manual melakukan switch setelah menerima alert (lebih aman untuk critical systems yang memerlukan verification)

Failback: Proses mengembalikan traffic ke primary system setelah primary telah diperbaiki. Failback bisa:

  • Automatic: Primary otomatis mengambil alih ketika healthy lagi
  • Manual: Administrator memutuskan kapan switch back (safer untuk verifying primary stability)

Live VM Migration: Memindahkan running VM dari failing physical server ke healthy physical server tanpa downtime. Proses:

  1. Copy memory pages dari source ke destination secara iteratif
  2. Pause VM briefly untuk copy dirty pages terakhir
  3. Resume VM di destination
  4. Total downtime: typically milliseconds

Checkpoint/Restart: Periodically save application state (checkpoint) ke stable storage. Jika failure terjadi, restart dari checkpoint terakhir. Trade-off: overhead dari checkpointing vs recovery time.

6. Data Replication Strategies ▼

Synchronous Replication:

  • Write operation dianggap complete hanya setelah data telah ditulis ke primary DAN replica
  • Zero data loss (RPO = 0)
  • Latency lebih tinggi karena harus menunggu acknowledgment dari replica
  • Cocok untuk: financial transactions, critical databases

Asynchronous Replication:

  • Write operation dianggap complete setelah ditulis ke primary. Replica di-update secara asynchronous (lag).
  • Potential data loss jika primary fail sebelum replica di-update (RPO > 0)
  • Latency lebih rendah
  • Cocok untuk: analytics, logging, non-critical data, geo-distributed systems

Quorum-based Replication:

  • Write dianggap complete jika ditulis ke W replicas dari total N replicas (W > N/2)
  • Read dianggap valid jika dibaca dari R replicas (R + W > N)
  • Memastikan consistency meski beberapa nodes fail
  • Contoh: Cassandra, DynamoDB, CockroachDB

DevOps & Software Development Life Cycle (SDLC)

1. Definisi DevOps ▼

DevOps adalah kombinasi dari Development (Dev) dan Operations (Ops). DevOps adalah praktik, filosofi, dan culture yang menggabungkan software development (pengembangan) dengan IT operations (operasional) untuk memperpendek SDLC dan menyediakan continuous delivery dengan high software quality.


Goals DevOps:

  • Speed - Rilis fitur lebih cepat ke production
  • Reliability - Kualitas aplikasi tetap terjaga meski frequent releases
  • Scale - Operasional dan development dapat scale bersamaan
  • Security - Security integrated ke dalam pipeline (DevSecOps)
  • Collaboration - Menghilangkan silo antara tim dev dan ops

3. Continuous Integration (CI) ▼

Definisi: CI adalah praktik mengintegrasikan code changes dari multiple developers ke shared mainline (main/master branch) secara frequent (biasanya multiple times per day). Setiap integrasi di-verify oleh automated build dan automated tests.


Goals CI:

  • Detect integration errors as quickly as possible
  • Prevent "integration hell" di akhir development cycle
  • Automated testing setiap kali ada code push
  • Fast feedback loop untuk developers

CI Pipeline Steps:

  1. Code Commit - Developer push code ke repository
  2. Checkout - CI server checkout latest code
  3. Build - Compile code, bundle assets, create artifacts
  4. Unit Test - Jalankan unit tests untuk verify individual components
  5. Static Analysis - Code linting, security scanning (SAST)
  6. Integration Test - Test interaction antar components
  7. Artifact Storage - Simpan build artifact (Docker image, zip, dll)

Popular CI Tools: Jenkins, GitHub Actions, GitLab CI, CircleCI, Travis CI, Azure DevOps, Bamboo.

4. Continuous Delivery (CD) vs Continuous Deployment ▼
AspekContinuous DeliveryContinuous Deployment
Definisi Code changes secara otomatis built, tested, dan prepared untuk production release. Tapi deployment ke production memerlukan manual approval. Code changes secara otomatis built, tested, DAN deployed ke production tanpa manual intervention.
Manual Step Yes - someone must click "Deploy to Production" No - fully automated end-to-end
Risk Lower risk karena ada human gatekeeper Higher risk, memerlukan very mature testing suite
Use Case Enterprise apps, regulated industries, apps requiring compliance sign-off Web apps, SaaS, consumer apps dengan mature automated testing

CD Pipeline Steps (setelah CI):

  1. Staging Deployment - Deploy ke staging environment yang mirror production
  2. Smoke Test - Quick test untuk verify deployment berhasil
  3. UAT / E2E Test - End-to-end testing di staging
  4. Performance Test - Load testing, stress testing
  5. Security Scan - DAST (Dynamic Application Security Testing)
  6. Approval Gate - Manual approval untuk production (hanya Continuous Delivery)
  7. Production Deployment - Deploy ke production servers
  8. Post-Deploy Verification - Health checks, monitoring alerts
5. Infrastructure as Code (IaC) ▼

Definisi: IaC adalah praktik managing dan provisioning infrastructure (servers, networks, databases) melalui code files, rather than manual configuration. Ini memungkinkan infrastructure di-version, di-test, dan di-deploy seperti application code.


Benefits IaC:

  • Consistency: Eliminates configuration drift (server A dikonfigurasi beda dengan server B)
  • Speed: Spin up entire environments dalam minutes, not days
  • Version Control: Infrastructure changes tracked di Git
  • Reusability: Templates dapat digunakan berulang kali
  • Disaster Recovery: Rebuild entire infrastructure dari code dalam hours

6. Containerization & Orchestration ▼

Containerization: Teknologi untuk packaging aplikasi beserta dependencies-nya (libraries, runtime, config files) ke dalam lightweight, portable container. Container berbagi OS kernel dengan host, making them more efficient than VMs.


Docker: Platform paling populer untuk containerization.

  • Docker Image: Read-only template yang berisi application + dependencies
  • Docker Container: Running instance dari Docker image
  • Dockerfile: Script untuk membangun Docker image
  • Docker Hub: Registry untuk menyimpan dan distribusi Docker images

Orchestration: Mengelola lifecycle containers: deployment, scaling, networking, load balancing, health checks, failover.

  • Kubernetes (K8s): De facto standard untuk container orchestration. Features: auto-scaling, self-healing, service discovery, rolling updates, secrets management.
  • Docker Swarm: Native Docker orchestration, simpler than K8s tapi less features.
  • Amazon ECS/EKS: Managed container orchestration di AWS.

Step 4: Buat Deploy Script (Manual CI/CD) ▼

Kita akan membuat script deploy sederhana yang dijalankan dari Laptop A untuk meng-update aplikasi di VPS secara otomatis.


A. Buat deploy script di Laptop A:

# Buat file deploy.sh di project folder
$ cat > deploy.sh << 'EOF'
#!/bin/bash

# Konfigurasi
VPS_IP="203.0.113.50"
VPS_USER="deploy"
APP_DIR="~/apps/my-cloud-app"
REPO_URL="https://github.com/username/my-cloud-app.git"

echo "🚀 Starting deployment to VPS..."

# 1. Push latest code ke GitHub
echo "📤 Pushing code to GitHub..."
git push origin main

# 2. SSH ke VPS dan pull latest code
echo "🖥️ Connecting to VPS and pulling updates..."
ssh $VPS_USER@$VPS_IP << 'REMOTE'
  cd ~/apps/my-cloud-app
  echo "⬇️ Pulling latest code..."
  git pull origin main

  echo "📦 Installing dependencies..."
  npm install --production

  echo "🔄 Restarting application with PM2..."
  pm2 reload my-cloud-app --update-env

  echo "✅ Deployment completed!"
REMOTE

echo "🎉 Deploy finished successfully!"
echo "🌐 Check: http://$VPS_IP"
EOF

# Beri permission execute
$ chmod +x deploy.sh

B. Jalankan deploy:

# Pastikan semua perubahan sudah di-commit
$ git add .
$ git commit -m "Update: new feature"

# Jalankan deploy
$ ./deploy.sh

# Output yang diharapkan:

Step 5: Setup GitHub Actions (Automated CI/CD) ▼

Jika ingin fully automated (push ke GitHub langsung deploy ke VPS tanpa jalankan script manual), gunakan GitHub Actions.


A. Setup SSH Key di GitHub Secrets:

# Di Laptop B (VPS), generate key untuk GitHub Actions
$ ssh-keygen -t ed25519 -f ~/.ssh/github_actions -N ""

# Copy public key ke authorized_keys
$ cat ~/.ssh/github_actions.pub >> ~/.ssh/authorized_keys

# Copy private key (tampilkan dan copy ke clipboard)
$ cat ~/.ssh/github_actions
# -----BEGIN OPENSSH PRIVATE KEY-----
# ... (copy seluruh isi) ...
# -----END OPENSSH PRIVATE KEY-----

# Di GitHub Repository:
# Settings > Secrets and variables > Actions > New repository secret
# Name: VPS_SSH_KEY
# Value: (paste private key di atas)

# Tambahkan juga secret:
# VPS_HOST = 203.0.113.50
# VPS_USER = deploy
# VPS_PATH = /home/deploy/apps/my-cloud-app

B. Buat GitHub Actions Workflow:

# Buat folder dan file workflow
$ mkdir -p .github/workflows
$ cat > .github/workflows/deploy.yml << 'EOF'
name: Deploy to VPS

on:
  push:
    branches: [ main ]

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
    - name: Checkout code
      uses: actions/checkout@v4

    - name: Setup Node.js
      uses: actions/setup-node@v4
      with:
        node-version: '20'

    - name: Install dependencies
      run: npm ci

    - name: Run tests
      run: npm test
      continue-on-error: true

    - name: Deploy to VPS
      uses: appleboy/ssh-action@v1.0.0
      with:
        host: ${{ secrets.VPS_HOST }}
        username: ${{ secrets.VPS_USER }}
        key: ${{ secrets.VPS_SSH_KEY }}
        script: |
          cd ${{ secrets.VPS_PATH }}
          git pull origin main
          npm install --production
          pm2 reload my-cloud-app --update-env
          echo "Deployment completed at $(date)"
EOF

# Push workflow ke GitHub
$ git add .
$ git commit -m "Add GitHub Actions CI/CD pipeline"
$ git push origin main

C. Hasil: Setiap kali Anda push ke branch main, GitHub Actions akan:

  1. Checkout code
  2. Install dependencies
  3. Run tests (opsional)
  4. SSH ke VPS dan jalankan deploy script

Monitor status di tab Actions di repository GitHub Anda.

Troubleshooting Umum:

MasalahPenyebabSolusi
Cannot SSH ke VPS Firewall block port 22, SSH service down, wrong key Cek UFW: sudo ufw allow ssh. Cek SSH service: sudo systemctl status ssh
502 Bad Gateway (Nginx) App tidak berjalan, salah port proxy, app crash Cek PM2: pm2 status. Cek logs: pm2 logs. Verifikasi proxy_pass port
Permission denied saat git pull SSH key tidak terpasang, repo private tanpa token Pastikan SSH key di ~/.ssh/authorized_keys. Untuk GitHub, gunakan PAT token
App tidak auto-start saat reboot PM2 startup belum di-setup Jalankan: pm2 startup systemd lalu pm2 save
Port 3000 tidak accessible dari luar App bind ke localhost saja Pastikan app listen ke 0.0.0.0: app.listen(3000, '0.0.0.0')
